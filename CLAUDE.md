# Videomancer program development — master reference

Distilled from ~80 programs' worth of builds, hardware sessions, and post-mortems (compiled 2026-08-16).
Companion: **[TECHNIQUES.md](TECHNIQUES.md)** — the pattern catalog (proven rendering/engine techniques with exemplar programs, costs, and dead-ends). Read it before designing a new program; add an entry when a new technique is proven.
Platform documentation is `videomancer-sdk/docs/` (program-development-guide, toml-config-guide, program-categories, vmprog-format, abi-format, ai-program-generation-guide, package-signing-guide, bitstream-compression, plus `fpga/`, `schemas/`, `video-standards/`). Consult those for platform basics; this file records only what was learned the hard way on top of them. Per-program deep history lives in the Claude memory dir.

**Platform**: iCE40 HX4K — 7680 LC, 32 EBR (128 kbit BRAM), **no DSPs** — at a 74.25 MHz pixel clock for HD. Each program = `<name>.vhd` + `<name>.toml` (optional `<name>.py` build hook); core entity at `videomancer-sdk/fpga/core/yuv444_30b/rtl/program_top.vhd`. Video is 10-bit YUV: luma unipolar (black 64), chroma signed about 512.

## Repo layout & workflow

- New programs go under `programs/ron/<name>/` — never `programs/lzx/` (that mirrors LZX-shipped programs).
- The primary reference for TOML schema, VHDL patterns, and framework conventions is `videomancer-sdk/programs/` (kintsugi, colorbars, stic, howler, sabattier, perlin, pong, mycelium) — canonical, authored by the framework creator. `programs/ron/` is secondary (may carry accumulated errors).
- Build one program: `./build_programs.sh <vendor> <name>` (e.g. `./build_programs.sh ron nimbus`) → 6 bitstream configs packed into `out/<HARDWARE>/<vendor>/<name>.vmprog`, the flashable artifact. Direct `make -C videomancer-sdk/fpga PROGRAM=<name> PROJECT_ROOT=programs/<vendor>/<name>/` is faster for syntax/timing iteration but produces no `.vmprog`. **Never** run `build_programs.sh` with no args or vendor-only (builds everything).
- **Never `rm -rf out/`** — it holds the deliverable `.vmprog` for every program (a reflexive wipe once destroyed 26 untracked vmprogs) and the build never reads it. Scoped clean rebuild = `rm -rf build/programs/<vendor>/<program>/` only.
- `program_config.bin` stale-cache trap: the builder only regenerates it if missing, so TOML edits (labels, presets, defaults) silently never reach hardware. Fix: `rm build/programs/<v>/<p>/program_config.bin` (and the `rev_b/` copy), confirm the "Converting TOML..." line appears, `grep -a` the binary for new labels. The bitstream cache likewise ignores TOML core-config edits — a rebuild finishing in ~0.01 s/config is a cache hit; `rm -rf build/programs/<vendor>/<prog>` and expect ~40 s synth per config.
- **Presets from the hardware**: when Ron dials a look in on the Videomancer, capture it with `./capture_preset.sh --preset N --name "Name"` (N from 0; N = current count appends, max 8) or `--defaults`; `--dry-run` first. It reads the device over USB serial, finds the TOML in `programs/ron` by program_id, auto-attaches the Videomancer to WSL via usbipd-win and detaches after (Windows loses its USB drive/MIDI while attached), and clears the stale `program_config.bin`; then rebuild the program. Prefer this over hand-typing preset values. Setup + caveats: memory `capture_preset_tool`.
- `program_type` gates input video: `synthesis` routes NO input, so `data_in.u/v` read code 0 = saturated GREEN on hardware while sims pass. Any program that reads `data_in` in ANY mode must declare `processing`.
- TOML pre-check: `python3 videomancer-sdk/tools/toml-converter/toml_to_config_binary.py <toml> /tmp/out.bin` (on error the build still "succeeds" with a stale binary). Params with `value_labels` cannot have numeric fields — use `initial_value_label`. `description` max 127 bytes; preset `name` max 15 chars (fails only AFTER all 6 bitstreams build). `categories` is a fixed 37-entry list — "Process", "Retro", "Palette", "Processing" are all invalid guesses. Never ship a reversed display range (`display_min > display_max`): the validator accepts it but hardware refuses to load the vmprog — invert the mapping in VHDL instead (turpentine).
- Git: no gh CLI/SSH keys on this WSL2 box; auth via Windows Git Credential Manager. Origin = bluecondition/videomancer-dev; the videomancer-sdk submodule tracks bluecondition/videomancer-sdk branch `router2`; upstream lzxindustries has diverged (removed hd_clock_divisor) — SDK updates mean rebasing the router commit.
- This WSL wipes /tmp mid-run — keep working/profiling files under home (or the session scratchpad), not /tmp.

## Standing rules & control design

- **Never set/change `hd_clock_divisor` without asking** — divisor=2 built clean but black-screened rev_b hardware. Close timing at the full 74.25 MHz clock, or surface the tradeoff and ask.
- **HD-first**: the primary target is HD (1080p, 74.25 MHz, hd_analog/hd_hdmi/hd_dual) — design the look, resource budget, and timing around HD from the start, and treat SD as a follow-up to adapt as needed (never let SD constraints shape or dilute the HD design). All 6 configs must still build to pack a vmprog, but HD is where the design is judged.
- **Resolution consistency** (Ron, 2026-10-17): every program must render the SAME picture at SD, 720p and 1080p — elements sized to screen height, layout spanning the width, round things round on 4:3 SD, nothing 2:1 stretched (pixel-level textures may stay pixel scale). HD HDMI is the main test bed, but build geometry resolution-independent from the start (virtual 1080-line coordinates from the timing ID `registers_in(8)(3 downto 0)`; TECHNIQUES "Virtual 1080-line coordinates", pilot mondrian v1.0.2), and **warn Ron** whenever SD or 720p will look different or must compromise.
- Working-on-hardware beats pixel-exact: use reference renders to localise defects, then spend the freedom on narrow operands and cheap approximations — preserve the LOOK, not the bits. Cutting a visible feature is different and still needs asking.
- **Default to building, not simulating** (reaffirmed 2026-08-16 — the drift toward over-simming is a repeated problem). The normal loop is: build, report post-route Fmax/LC, and let the user flash it and describe what they see — hardware eyes are the primary verification, and each sim costs 30 s–3 min plus PNG clutter. Do NOT sim to re-verify known-working code, logically-equivalent refactors, or restored features. Sim only when it's genuinely logical and necessary: the user asks; a NEW visual artifact can't be reasoned out from the code; or render-correctness is the deliverable AND it already failed on hardware once (a clean Python proto doesn't count — float protos miss fixed-point bugs). When in doubt, build and hand it over.
- **Bold always-on controls**: every knob/switch must visibly change the picture at ANY slider position — never gate a control behind a zone/mode of another control. The headline slider's 100% must be a designed climax scene, not math degenerating. Bias effect strength bold (redshift needed ~32× the "reasonable" scaling); when in doubt, overshoot and clamp. Switches = instant look-flips.
- The headline performance control goes on the **P12 slider** (`registers_in(7)`); rotaries are set-and-forget.
- No more coarse-field-overlay programs (mercurial/redshift/kudzu genre rejected). Favor immediate same-frame per-pixel response and structural re-rendering — the image redrawn AS lines/glyphs/geometry, not a layer over it. Relatedly: when the user says a filter is "not interesting," reconstruct the image from new primitives; adding effects to a visible original raster never lands (turpentine).
- Never multiply a knob that already spans its full range by a second control — it eats the first knob's travel. Never give a physics/motion program a switch that halts it completely (an unnoticed switch reads as a broken build).
- User-reported saturation/brightness percentages are proc-amp readings: 50% = bit-exactly unchanged; build symmetric deviation around unity.
- For a known graphic design, get exact vector coordinates up front — verbal descriptions cost 11 wrong iterations on overlook. Calibrate feature sizes from the reference image, not evocative words.
- A tool-call rejection may be an accidental stop-button press, not a veto — note what you were doing and ask, or continue with the next reasonable step.

## VHDL traps

- `to_unsigned(N, W)` silently wraps when N ≥ 2^W (`to_unsigned(64, 6) = 0`) — symptom: a counter/step "doesn't advance". Widening to the result width costs nothing; grep `to_unsigned(` when anything is stuck. Same for out-of-range sentinels in `to_signed` — pick in-range sentinels.
- `shift_left(x, n)` keeps the operand's own width and discards top bits — shift-add rewrites of multiplies are NOT free (`"*"` widens, shifts don't). `resize` BEFORE shifting: `shift_left(resize(s_k6, 20), 3) - resize(s_k6, 20)`, never `resize(shift_left(s_k6, 3) - s_k6, 20)`. Symptoms are knobs that cycle instead of ramping, or pinned dead at 0.
- `resize(signed, N)` narrowing keeps sign + rightmost N−1 bits — an |value| that legitimately reaches 2^(N−1) folds in half. Negate at full width, then **slice**; use a slice, not resize, when you want modulo wrap.
- The `&` concat operator always returns an ascending range (`0 to N`); passing `signed('0' & x)` into a function that slices `v(4 downto 0)` errors. Assign to a declared signal first.
- Symmetric xor packs collapse: `(x & y) xor (y & x)` depends only on `x xor y` — diagonal cells share hashes; `f_hash(x, x xor const)` is a constant. Use `(a xor rotate_left(b,5)) xor seed`, or `x + odd_const`. **Numerically spot-check every new hash** (h/v/diag correlations over a grid) before trusting it. Also: xor/rotate-only hashes are linear over GF(2) — at least one integer ADD is required for real mixing (prefer shift-and-add over shift-and-xor; the carries are the nonlinearity).
- `a + b >= WRAP` on same-width operands loses the carry — compute wrap tests one bit wider (penrose).
- A slice of a signed immediate is still signed — `to_integer(v_imm(3 downto 0))` turned shift 10 into −6 (cubist).
- `(expr srl n)(1 downto 0)` is illegal VHDL — shift into a temp variable first.
- `x * to_unsigned(8+b, 5)` infers a real multiplier even when b is a loop constant — write explicit shift-adds in a `case`.
- `mod`/`/` by non-power-of-2 is a synthesis disaster (~18 ns); variable-index register arrays synthesize as giant mux trees; parallel for-loop array updates make long combinational chains — serialize them.
- GHDL synthesis crashes (`netlists-memories.adb` internal error) on parallel reads of an array-of-arrays constant — emit N separately-named 1-D constants and unroll.
- Suspected yosys miscompile of variable-written self-referencing hold registers (etchplate) — write hysteresis holds as plain clocked-if. yosys `fsm_extract` once mis-compiled a 40-state FSM (RTL sim correct, hardware wrong): `attribute fsm_encoding of fst : signal is "none"` and post-synth iverilog-sim any large-FSM program.

## BRAM/EBR rules

- Inference needs the canonical 1W1R shape: exactly ONE write statement (mux data/addr/we into it — a second write in an elsif arm turns a line buffer into 9205 LC of FFs), no conditional reads (`if par then a else b` maps to logic — read both, mux registered outputs), full power-of-2 depth declaration (`0 to 255`, not `0 to 19`; `ram_style` alone does nothing).
- **`no_rw_check` on every collision-free RAM** (found 2026-10-09, damier). VHDL read-before-write semantics on iCE40 EBR (collisions undefined) make yosys emulate it with a delayed write port + bypass mux: ~74 FF + 43 LUT per 32-bit RAM, on EVERY RAM that is both written and read, silently. `attribute no_rw_check : boolean; attribute no_rw_check of r_ram : signal is true;` removes it (GHDL warns "unhandled attribute" but passes it through), but it only takes effect when the read-data register has an init value (`:= (others => '0')`); without one GHDL builds the sync port itself and yosys ignores the attribute. Verify `grep -c emulate_transparency` in the yosys log = 0. Only for RAMs that provably never read the address being written (bank-split tables, offset rings, register files with their own forwarding). damier: −231 LUT / −225 FF across 9 RAMs. Check every write enable is a one-clock pulse first: pulp's sequencer left a slot RAM's `we` high all frame (harmless under emulation, a read collision on every pixel once the attribute is on).
- **Read-modify-write infers only in the PIPELINED shape**: a registered read (`rd <= ram(ra)`), a fabric re-register, the modify, then a write from its own clocked process (`if we then ram(wa) <= wd`) infers one SB_RAM40_4K (tested 2026-10-10, wake: motion grid `M = max(d, M - dec)` and column accumulators). Write data that depends combinationally on a same-cycle read of the memory becomes thousands of FFs. When the shape can't be pipelined, design around it (snoop reads, ping-pong banks, separate accumulate passes).
- Pad EBR-stored words to a power-of-2 width — a 30-bit word split across a 16+14 RAM pair posterized video on hardware while sims diffed bit-exact. Sims run the behavioural array and CANNOT catch BRAM-mapping bugs.
- GHDL returns defined data on same-address read-during-write; iCE40 EBR returns UNDEFINED — invisible in sim, black-screens on hardware. Ping-pong banks by row/frame parity instead.
- Register BRAM read data into a fabric FF before ANY arithmetic (EBR clk-to-q ~2.15 ns + routing from EBR columns) — applies in vblank FSMs too. And a registered-in/out ROM gets its output register ABSORBED into the EBR: if critical paths start at `<rom>.RDATA`, add a SECOND fabric register (tell: RAM count jumps + LC drops while Fmax regresses).
- FF arrays pay a hidden mux/decode tax — any 16+-entry table or multi-slot state belongs in one EBR with a time-shared port (sequencer writes in vblank, pixel path reads during active). Two read ports = duplicated RAM = router seed-crashes; time-mux one port. N expressions over the same constant array infer N ROMs — read the array once into a variable.
- Line-buffer write addr = read addr delayed by the EXACT pipeline depth of the write-data computation; off-by-N = diagonal drift. Sim-test with vertical bars — anything axis-aligned coming out diagonal means the delay is wrong. (Or sidestep it: dual-bank buffer with write parity captured at read-issue, see TECHNIQUES.) Same class: a read-modify-write SWEEP must write back at the tap where the BRAM data actually arrives — 2 clocks after the address is issued (address reg + output reg). Pyro/fireworks wrote back at a 1-clock tap, so every decay sweep slid the canvas one cell right (months of 'trails always go right' blamed on stars and dither).

## Hardware & video-signal contracts

- **Blanking gate**: any program computing output from `data_in` must gate y/u/v to neutral (y=64, u=v=512) whenever latency-aligned `avid`='0' (gate one stage before the output register). Violation = rail-to-rail green/magenta over the whole picture; **no sim catches it** (the image-tester scores only the active region).
- **One latency for all modes**: the program must present a single sync-tap latency to the core across all modes — a mode-dependent deeper tap = green hue + noise lines on hardware while every sim and icetime pass. Budget a delayed path's base delay inside the existing latency via shift-invariance (make ±N displacement one-sided: `read 1+disp back, disp 0..18`); if latency truly must grow, grow it for ALL modes. Also keep RAW input video shallow: carried ~12-15 FFs deep through the program (even at one uniform latency, syncs matched) it went green + noisy on HD HDMI three times (cascade v1.4, rollthebones v0.2/v0.5) while generated content at the same depth was clean — mechanism unknown (core input capture measured fine). Tap video early (a few px shift is invisible) and make bypass a 1-cycle passthru; HW-confirmed fix on rollthebones v0.6.
- **The encoders get NO data-enable** (core_top: only the 4:2:2 bus + hsync/vsync go to the ADV7393/ADV7513), so they pair Cb/Cr by counting from hsync, while the core's 444→422 packer restarts on Cb at every avid rise and resets at every avid fall. An avid that wanders a clock against hsync, or drops out mid-line, swaps U/V for that line: thin coloured lines over coloured areas only (neutral U=V=512 is immune), faces flipping hue, and a program-side U/V swap that changes NOTHING. Synthesis programs fix it by generating their own avid: start 2–3 clocks after the source's first avid rise, choosing whichever keeps the hsync→start PARITY at the source's usual value (1-bit toggle + saturating vote), end on the program's own pixel count — ~25 LC, HW-CONFIRMED on cubist v0.3.3 (lines gone, colours correct with the usual swap). Also HW-confirmed on aurora v3.0.2 (HD HDMI): a processing-declared program that draws its OWN colour needs it too — passing the source avid through gave thin red lines across the rainbow band. (A 12-bit locked-offset version cost 250 LC — only parity matters.) The standing "hardware swaps U/V" is probably this same hsync-offset parity. Processing programs that replay a STORED line on other rows (drape) hit the same parity as a per-row swap: latch the hsync→avid parity per line and for the capture row, and swap U↔V at output where they differ (keep U/V pairs coherent). No swap gives a green/magenta cast; a parity-forced single chroma read gives dark lines at colour edges. HW-validated on drape v1.3 (see TECHNIQUES).
- **Line lengths wander on analog sources**: an avid-gated per-pixel accumulator (DDA) with a fixed end-of-line correction piles up the ±1-pixel line-length jitter down the screen (a wavy image), and a width measured on one odd line shears the whole field. Step a FIXED count per line (latched per field, carried into the front porch if a line runs short) and use that same count in the correction. Never trigger per-field work off hsync edges either (a doubled edge fires it mid-picture): use "avid absent for 2 line-widths". Sims have perfect timing and catch none of this (cubist v0.3).
- **Per-line clock budgets**: HD 2200 clks/line (1920 active / 280 blank); SD/NTSC **858** (720/138) — NOT 1716, SD `prog_clk` is 13.5 MHz; PAL 864; 720p 1650. Overrunning a per-line pass degrades silently. N-lines-early buys latency, not throughput — a late pass misses the next trigger entirely (killed nacre).
- **The HD hardware is 1080p PROGRESSIVE** (1080 active lines) — active-row counters need ≥11 bits (a 10-bit counter wraps at line 1024 and aliases tile grids).
- **Interlace**: bottom field = `field_n='0'`, top = `'1'`; wrong-field seeding = crawling 2 px comb on diagonals, catchable only with `--video-mode 1080i5994`. Per-line accumulators/DDAs must advance on ACTIVE lines only (advance at active-video fall, copy at hsync; don't mux the adder output — that costs ~8 MHz) or the two fields diverge by 2·inc = 30 Hz twitter. Line-keyed hash/noise keys on the true frame line (`aline & field`), not the field line. Refresh cell state on ONE field only under interlace.
- **NO input has field_n** (SD included): core_top ties `field_n <= '1'` on all six inputs (SD and HD, HDMI and analog), so a bottom field never reaches a program and SD is effectively line-doubled. Detect interlace from the timing ID only (`registers_in(8)`: 0 = 480i, 8 = 576i, 1/2/10 = 1080i); a field_n-toggle detector is dead on hardware (cubist, deadchannel, ribbon, pixelbeach drew SD 2:1 tall until the 2026-10-17 sweep), and a power-up `prev_field` of '0' fakes one interlaced field after load (hypnos/cubist start-up glitches). A 1080i source (computers and players pick 1080i60, since there is no 1080p60 timing) gives identical field_n on both fields, so any program comparing or picking fields by field_n silently mixes them. Wake v0.2.1 saw edge-clustered false motion on a FROZEN computer image. For a same-parity cadence, use a per-field toggle on the guarded vsync edge (parity identity not needed), or the SDK `video_field_detector` (sync phase). The image tester's 1080i stimulus DOES toggle field_n and has NO half-line vsync offset, so it can't catch this: emulate hardware by tying field_n high in a scratch copy.
- **Vsync is hostile**: analog vsync serrates — MULTIPLE edges per field. Resets are idempotent and safe; any toggle/increment/bank-swap needs the saw-active guard (set flag on `avid='1'`, act once, clear). GHDL vsync is one clean edge — sim can never catch this. And never latch frame HEIGHT at vsync (the line counter zeroes on blanking hsyncs first — reads 0; capture on active lines in the counter's increment branch). Reset warm-up guards on lines with no active video, not the vsync edge (decoders assert vsync early). Anchor frames on the vsync EDGE, never the LEVEL: a level-cleared anchor (`if vsync_n='0' then clear elsif avid ... fire`) never fired on hardware, so every per-frame latch was dead (deadchannel v1.1; fixed in v1.3).
- **Chroma code 0 is saturated GREEN, not black** (RGB ≈ 0,542,0). Bit-replicated narrow chroma has NO neutral code — quantize chroma in steps of 128 and expand by shift (`u3 & "0000000"`, round with +64). Every zero-defaulted RAM/register that can reach the screen needs an explicit neutral-chroma reset — including buffers copied wholesale and modes that "don't use" chroma (green flashes on mode toggles, not just power-on).
- **HD HDMI thick bright bars**: bars several lines tall that start at a random x, run to the right edge and flash. They are triggered by the PROGRAM's picture: sharp, near-full-swing pixel-to-pixel edges in motion (static pictures don't bar). Ron is firm it is never the cable or display. The fix, hardware-A/B-confirmed on damier v0.4.4 (a switch toggling it on one fixed placement), is output conditioning just before the blanking gate:
  - a horizontal [1 2 1]/4 smoothing on Y, U AND V (keep a 2-pixel window, output the centre);
  - luma scaled toward black, `y − (d>>3) − (d>>4)` with `d = y − 64` (white ~775).

  It costs +2 stages and ~150 LC, at the same latency in all modes. A luma-only smoothing (ribbon) did not hold. Apply it to any program that bars; for a program that draws crisp high-contrast moving edges, build it in from the start.
- **Cap drawn luma at ~768** — full-scale Y clips all RGB and kills chroma on hardware. Generated palettes: Y = 64 + y·876 (black is 64, not 0 — a y·1023 mapping crushed inferno's dim ramp ends below black), chroma 512 ± c·896.
- **Control registers**: rotaries 1–6 = `registers_in(0..5)`; toggles 7–11 = BITS of `registers_in(6)` (switch N reads `registers_in(6)(N-7)`); P12 slider = `registers_in(7)`. Wiring a toggle to `registers_in(8)` compiles and silently does nothing.
- Field-latch any parameter feeding a multi-line detector window (knob updates mid-frame tear across line buffers and read as a full-width edge); display-side params can stay instant. Never read SPI registers inside the vsync decision cone (slider carry chains cost ~5 MHz) — decode to free-running 1-bit flags. Add a glide filter (ease by diff>>3, no snap) on any control where pot ADC noise shows; deadband decision-side controls.
- Screen-geometry features derive from runtime-measured width/height as fractions — never fixed pixel constants tuned to one mode.

## Timing closure & fit (iCE40 HX4K @ 74.25 MHz)

**Reading results**
- Judge timing from the LAST "Max frequency" line per clock (post-route), never the first (pre-route placement estimate — can be anti-correlated with routed results). The builder's "✓ Completed (seed 6)" on the final retry can be a best-effort MISS — re-verify any config that only completed on the last seed. Acceptance = last post-route line PASS + `.bin` exists + `iceunpack` OK.
- router2 (the build default; router1 stalls for hours on congestion) is multithreaded-NONDETERMINISTIC: same json + seed can pass at 75.9 and fail at 65.8 under load. Margins near Fmin are run-marginal. Its failure mode is a silent stall (`overused=` stuck); the builder wraps make in `timeout -k 5 ${MAKE_TIMEOUT:-360}`.
- router1 can route FAR better than router2 on some netlists: cubist v0.3 got 75-78 MHz on all HD configs with router1 (mostly seed 1) where router2 gave 49-60 on every seed. Oracle v2 (the same microcoded engine) repeated it exactly: router2 missed all 6 seeds on every HD config, router1 closed 6/6 on seed 1 — try router1 first for engine-based programs. When router2 misses everywhere, rebuild with `NEXTPNR_ROUTER="--router router1" ./build_programs.sh <vendor> <prog>` before restructuring. Note a bare `make` (no ROUTER=) already uses router1 -- don't compare a bare-make result against the builder's router2.
- `icetime` is pessimistic and NOT the flow's gate (exception: pixelbeach used it after a real HW timing miss). Toolchain env: `source videomancer-sdk/build/oss-cad-suite/environment`.
- hd_analog/hd_dual report clock `ADV7181C_CLK`, hd_hdmi reports `ADV7611_CLK` — grep `"Max frequency for clock"` generically; hd_dual can print twice, the LAST is routed.

**Strategy**
- Read the nextpnr critical path, don't guess. Profile:
  ```
  nextpnr-ice40 --hx4k --package tq144 --pcf <pcf> --freq 74.25 \
    --json <build>/bitstreams/hd_analog.json --asc /tmp/x.asc \
    --seed 1 --router router2 --timing-allow-fail -l /tmp/p.log
  awk '/Critical path report/,0' /tmp/p.log | grep -ao "c[0-9]*_[a-z0-9]*\|s_[a-z0-9_]*" | sort | uniq -c | sort -rn | head
  ```
- When "just short," measure the SEED SPREAD first (~6 seeds in parallel) — one unchanged netlist routed 72–86 MHz across seeds (clacker; three successive "fixes" there were all placement noise). But seeds cannot close a real deficit (pulp's 6% gap needed restructuring). A moving critical path across edits (different path, same ns) = several routing-bound paths — remove logic instead.
- If the critical path's FIRST hop out of a register is mostly routing (e.g. 7 of 13 ns crossing the die), suspect a HIGH-FANOUT net, not depth — duplicate the driving register once per consumer with `attribute keep` (yosys `opt_merge` re-merges them otherwise) so the placer can sit each copy beside its own sink. Pipelining cannot fix a single hop and logic removal is the wrong lever; gilt's shared mix coefficient feeding 3 multipliers cost ~6 MHz and a 68–84 MHz seed spread.
- Check the ns split: ~10 ns routing vs ~4 ns logic = congestion (pipelining REGRESSES it; only logic removal helps). Mostly-logic = a fusion problem (split the stage). At 90%+ util, distinguish by ablating a feature before cutting anything. Congestion can also be net TOPOLOGY: nacre's hd_dual closed by cutting 8 chained-RAM nets to 6 at identical LC — reduce net count before logic.
- Vblank sequencers and per-frame cones are fully STA-timed at the pixel clock — nextpnr doesn't know they're quasi-static. One small op per state (states are free); build per-frame terms one add per step; align slot ranges to power-of-2 boundaries so table indexes are literal low bits; run all per-frame products on one serial shift-add multiplier (sequential multiplies that feed each other need done-handshakes — a stale read renders fine but MOVES wrong, and no still sim catches it; shared-mult products are valid 2 cycles after set).

**Fit & high utilization**
- A late tap into the FF video delay pipe is not free: yosys prunes the pipe's unread y/u/v chains, so the first read of `pipe(14).u/v` un-prunes ~450 FFs at once (warpfield overflowed to 7722 LC). Carry a late video sample in a 16-deep EBR circular buffer (2 EBR; read pointer = write pointer − (depth needed), plus one fabric re-register) and keep the FF pipe for syncs.
- Target ≤ ~94% LC for routed closure at 74.25. At 90%+, added pipeline registers can REGRESS timing (pulp: a correct 2-stage split failed all 6 seeds); prefer REMOVING logic, and measure all 6 configs — HD Dual has the most I/O pressure and breaks first. At >90% the packer inflates LC, so reclaimed base LC helps twice.
- Ablation method when overflowing: standalone `yosys -m ghdl -p 'ghdl --std=08 <pkgs> program_top.vhd <prog>.vhd -e program_top; synth_ice40; stat'` (~90 s), diff LUT/carry against ablated copies in parallel. Stubs must keep outputs LIVE (drive from LFSR) — constant-tying sweeps downstream logic and lies. Standalone counts UNDERSTATE near the cliff; use them to rank, only a full build proves fit. Hand LC estimates were off by 3×.
- Usual hogs, in order: runtime-indexed register arrays (→EBR), per-pixel geometry that can become sprite/silhouette ROMs, big sequencer case machines (every branch's adder is separate hardware), variable-shift barrels (a case over fixed bit-slices is usually enough; or trade a barrel for a small multiply), duplicate work algebra can derive, constant multiplies with many set bits (yosys makes one adder per set bit — rewrite in canonical signed-digit form: warpfield's `* 0x9E37` went 9 → 5 adders per shell, −384 LUT).
- Pixel-path stage discipline: every multiply gets a stage to itself (even 8×9); one op per stage after a BRAM read; split multiply OPERANDS hi/lo (truncating the product does nothing — yosys already pruned unused bits); pre-bias per-frame constants so pixel stages are pure slice-selects and zero-tests; register barrel shifts whose amount is control-derived; separable X/Y tests one stage, combine next; build all N candidates in parallel + shallow-tree argmax (serial argmax = 35 MHz); 30/32 EBR is a router congestion cliff, 20/32 comfortable.
- Rebuild mechanics: a config failing by <2 MHz in a full build often passes rebuilt alone (less machine load) — `make ... CONFIG=<cfg> SEED=<good>` into `build/programs/<vendor>/<prog>/rev_b/bitstreams/` (rm the stale .bin first), then repack: `videomancer-sdk/tools/vmprog-packer/vmprog_pack.py --no-sign --hardware rev_b --toml-path <toml> <HW_BUILD_ROOT> <out.vmprog>`. Hand-installed bitstreams don't survive the builder's retry loop — land good seeds via `SEED=<base>` within `SEED_MAX_RETRIES` (default 6), or `NO_TIMING_RETRY=1`. yosys abc9 "Boxes are not in a topological order" is netlist-shape-sensitive — seed retries never help; restructure the offending logic. Known trigger (roulette): a `case` whose arms each add a different constant to a variable and then clamp — pre-register the per-arm offset one stage earlier and do a single add. Diagnose by parallel standalone-yosys ablation (~3 min each). Don't `pkill -f build_programs` in the same command that launches a build — it self-kills.

## Simulation practice

Everything below applies only once a sim is actually warranted — the default is build + hardware check, per the standing rule above.

- Headless image sim (no bitstream, ~20 s/frame): from `videomancer-sdk/tools/vhdl-image-tester`, `source videomancer-sdk/build/oss-cad-suite/environment`, then
  `./.venv/bin/python run.py simulate <prog> --image IMG.png --programs-dir /home/ron/videomancer-dev/programs/ron --set rotary_potentiometer_6=1023 --warmup-frames 2 --capture-frames 1 --output out.png`. GHDL `cannot find -lz`: symlink `libz.so.1.3` → `libz.so` and extend `LIBRARY_PATH`.
- Register keys: `rotary_potentiometer_1..6`, `toggle_switch_7..11`, `linear_potentiometer_12`. Unset registers take the TOML `default_value` (toggles that default ON sim active); enum rotaries with `initial_value_label` sim at 512, not the labelled default — `--set` explicitly for deterministic captures. Check the sim's exit status before reading the PNG (a failed run leaves the stale image).
- The stimulus hblank is a FAKE fixed 64 clocks (real: 138 SD / 370 HD) at every decimation. Per-line engines must satisfy `pass cycles ≤ W/decim + 64` or they break in sim only; designs needing >64 hblank cycles starve in sim but work on HW.
- The stimulus vblank is likewise a fake 8 lines: a vblank engine needing more than 8·(W/decim + 64) clocks never finishes in sim (1080p/dec 2 = 8,192) — render at a wider raster (720p60 dec 1 = 10,752; 1080p dec 1 = 15,872). Real: HD ~99k, NTSC ~14.5k (cubist's engine needs ~9.5k). Honest SD test: `--video-mode ntsc --decimation 1`. Sim raster = video_mode/decimation (default 480×270 progressive), not the image size; frame 1 publishes W/H defaults, frame 2+ measured.
- Decimated sims are unreliable for phase-accumulator/zoom engines, sub-pixel detail, throughput claims, and grid geometry (small dabs alias into stars; coarse knot grids render polygon contours) — verify at `--decimation 1` with `--warmup-frames` ≥ the vblank-multiply settle time (≥12 for chained sequencers). Derive screen-centre from measured width/height — the sim feeds a shrunken stream.
- **When hardware shows an artifact the sims don't, reproduce it in RTL at the HW raster with the user's knob settings (`--video-mode 1080p2997 --decimation 1`) BEFORE redesigning anything.** damier's lens ring sat at the table end (724 px from the centre); every 480×270 sim kept it off-screen. A numpy "bit-accurate" model encoded the intended pipeline and agreed with it. Two misdiagnoses shipped before one full-HD sim found it, a pipeline-phase bug. To make 1080p sims affordable, bypass knob glides in a sim-only copy of the program (3 warmup frames, ~14 min a frame-set, several in parallel).
- Colors: the sim renders standard BT.601; the HARDWARE swaps U/V (HW-reconfirmed 2026-07-27). Author internals in BT.601 and swap at exactly two points (input latch, output compose; never the dry path) — sim previews of generated colors then show swapped hues, which is CORRECT. Judge structure in sim, hue on hardware.
- Verify new engines by pixel-diffing the GHDL render against a bit-accurate NumPy model (target 0 pixels; see `sim-vs-model pixel diff` + the RTL-faithful Python cycle model in TECHNIQUES). Check each frame's white fraction before trusting a 0% mismatch — black ink on black ground passes trivially. Sweep-test every knob feeding a sequencer at the RTL's real widths (morsel `check_frame_math.py` pattern) — stills can't reveal wrap faults. Sim threshold programs with a noise+gradient stimulus. Sim BOTH progressive and `1080i5994` before shipping.
- Sim CANNOT catch: blanking-gate corruption, mode-dependent latency, vsync serration, BRAM mapping/read-collision bugs, real-blanking budgets, hue correctness, knob-sweep arithmetic, stale sequencer handshakes. Build+timing verify nothing about the image. If it flashes/glitches only at HD while sim is clean, suspect HD timing closure before the algorithm.

## Reference constants

- Calibrated CGA palettes (3×2, 10-bit YUV, U/V-swapped): `programs/ron/cga/cga.vhd` (`C_CGA_PAL`). Scope-verified ROYGBIV+black table (U/V-swapped BT.601; Red = Y 328, U 960, V 360): memory `phosphor_rainbow_palette`. Never start from unswapped BT.601 for generated hardware output.
- `proc_amp_u` unity: contrast 512, **brightness 512, not 1023** (1023 = +1.5, saturates all chroma).
